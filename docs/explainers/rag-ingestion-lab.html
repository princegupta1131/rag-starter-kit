1

Read the file and get the plain text

Extraction

The file is opened and only the words are kept. Formatting symbols are dropped, and the page number is remembered.

See it with the handbookREAL FILE
Before: the file

After: plain text

Why?

The search and the AI only understand words. Symbols like ## or Word's hidden XML are noise. The page number lets an answer say "see page 3".

The science, simply

No AI here, just careful reading. One exception: a picture is described in words by a vision model, so a chart or a photo becomes text the search can find.

Where in the kit

ingestion_service/steps/step1_extract.py reads PDF, Word, TXT, Markdown, CSV, JSON and HTML. Images: step2_caption.py.
Go deeper: what can go wrong

Bad text in means wrong answers out. Scanned PDFs are pictures of text and need OCR first, which the kit doesn't include. Some Hindi PDFs store letters in a scrambled order and need a Word copy instead. In the app, open a document's View chunks to check what was really extracted.

2

Cut the text into small pieces

Chunking

The text is cut into pieces of about 200 words. Each piece can be found on its own, like an index card in a drawer.

Try it: pick a piece sizeREAL TEXT · SAME RULES AS THE KIT
Before: one long text
→
After: pieces

Why?

One summary of a whole manual would be a blur of every topic. Small pieces let the search hand the AI exactly the paragraph about leave, not the whole handbook.

The science, simply

Smaller piece = sharper meaning, but less context. Bigger piece = more context, but mixed topics. About 200 words is a good middle. The overlap repeats the end of the previous piece, so a sentence at the border is never lost.

Where in the kit

step3_chunk.py. Settings in backend/.env: CHUNK_SIZE_WORDS=200, CHUNK_OVERLAP_WORDS=40. A sentence is never cut in half.
Go deeper: exactly how the kit cuts

1. Split the text into sentences. 2. Add whole sentences to a piece until the next one would pass 200 words. 3. Start the next piece with the last sentences of the previous one, up to 40 words. 4. Skip exact duplicate pieces, like repeated headers. With these rules the real handbook becomes 2 pieces in the database, of 199 and 185 words (they also include the title and the "try asking" list that this demo leaves out).

3

Turn the meaning into numbers

Embedding

An AI model reads each piece and gives back a list of 768 numbers. Think of them as GPS coordinates for meaning: texts about the same thing get coordinates close to each other.

The meaning map: where does each question land?REAL SCORES

A simplified picture: the real model uses 768 directions, not 2. The topic groups and the line to the closest sentence follow the real similarity scores.

Why?

People don't use the document's words. Priya says "holidays", the handbook says "unused days". Numbers for meaning let us match them anyway, even across languages.

The science, simply

The model is a neural network trained on billions of examples. Texts that mean the same were pulled closer, unrelated texts pushed apart, until closeness in numbers became closeness in meaning.

Where in the kit

step4_embed.py sends each piece to Gemini's gemini-embedding-001 model. EMBED_DIM=768.
Go deeper: inside the model, and all 768 numbers

1. Tokens: the text is split into word pieces the model knows (carri · ed · over · unused · days). 2. Attention: a transformer reads all the pieces together, so each word is understood in context: "leave" next to "annual" means time off, not "leave the room". 3. One vector: the layers are pooled into one list of 768 numbers for the whole piece.

No single number means "leave". Meaning is spread over all 768, like a fingerprint. Here are all 768 numbers of piece 1 (blue = positive, pink = negative, darker = bigger):

4

Measure how close two meanings are

Cosine similarity

Picture each list of numbers as an arrow. If two texts mean the same, their arrows point the same way. The score is the cosine of the angle between them: 1 = same direction, 0 = unrelated.

See it: Priya's question against three handbook sentencesREAL SCORES, DRAWN AS REAL ANGLES

Why?

We need one number that says "how close is this piece to the question?", so all the pieces can be ranked and the best ones picked.

The science, simply

Cosine looks only at direction, not length. A short question and a long paragraph can point the same way. That's exactly "same meaning, different length".

Where in the kit

Postgres does it: 1 - (embedding <=> question) in repositories/chunks.py. <=> is pgvector's cosine distance.
Go deeper: try the angle yourself, and the formula

cosine = 0.80 Change the length: the score doesn't move.

The formula: cosine = (A · B) / (|A| × |B|). Multiply the two lists number by number, add it all up, and divide by the two lengths. With 4 numbers:

Real vectors do the same with 768 numbers. Gemini's vectors here aren't length 1 (this one is 0.59), and that's fine: cosine ignores length.

5

Save every piece in a searchable database

Postgres + pgvector

Each piece becomes one row in Postgres: its words, its 768 numbers, and its keywords. A special index makes the search fast, like highways on a map.

See it: the real rows for the handbookREAL DATABASE
Try it: find the closest point to a questionSIMULATION
Check every row–checks
Use the index (HNSW)–checks

Why?

Everything in one place: words for the answer, numbers for meaning search, keywords for exact-word search. Normal SQL still works for filters and deletes.

The science, simply

Checking every row is fine for 100 rows, far too slow for 10 million. The HNSW index links each point to its neighbours, so a search hops towards the question instead of checking everything.

Where in the kit

Table and index: backend/sql/migrations/001_init.sql. Saving: step5_store.py. See the rows yourself in pgAdmin (Setup Guide, Step 8).
Go deeper: the SQL behind it
-- turn on pgvector, store 768 numbers per piece, and the keywords
CREATE EXTENSION IF NOT EXISTS vector;
embedding  vector(768),
tsv        tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED

-- the index that makes meaning search fast
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

-- meaning search: the 20 pieces closest to the question
SELECT content, 1 - (embedding <=> :question) AS similarity
FROM chunks ORDER BY embedding <=> :question LIMIT 20;

HNSW is approximate: it can very rarely miss the single best match, which is why the kit fetches 20 candidates, not 1.

What we have now

Every piece of the handbook is saved with its words, its meaning as numbers, and its keywords. This happens once, when the document is uploaded.
