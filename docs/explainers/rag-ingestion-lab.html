STEP 0 · THE PROBLEM

Why not just save the text in a database?

An employee asks: "Can I carry over unused holidays?" The handbook never uses the word "holidays". It says "Up to 5 unused days can be carried over". A normal text search looks for matching letters, so it finds nothing. People ask in their own words; RAG has to search by meaning.

STEP 1 · EXTRACT

Get plain text out of the file

Files store text with formatting: Markdown symbols, Word XML, PDF layout. The AI and the search only need the words, so the first step pulls out clean text and remembers the page it came from.

  • PDF: text page by page, so answers can say "page 3".
  • Word, Markdown, HTML, CSV, JSON: the text, without markup.
  • Images: a vision model writes a description, which then becomes text (step "Caption").

Science: nothing clever yet. This step is about being faithful: garbage text in means wrong answers out.

STEP 2 · CHUNK

Cut the text into overlapping pieces

One vector for a whole 50-page manual would be a blurry average of everything. So the text is cut into chunks of about 200 words. Each chunk gets its own vector and can be found on its own.

  • Too big: the chunk covers many topics and its meaning gets blurry. The AI also reads more text than it needs.
  • Too small: a chunk loses context ("it expires on 31 March", but what does?).
  • Overlap: each chunk repeats the last ~40 words of the one before, so an idea that crosses a border is still whole somewhere.

How the kit cuts: it never splits a sentence. It adds whole sentences until the size is reached, then starts the next chunk with the previous chunk's last sentences. Try the sliders.

STEP 3 · EMBED

Turn each chunk into a point in "meaning space"

An embedding model is a neural network that reads a piece of text and outputs a list of numbers, here 768 numbers. That list is a position in a 768-dimensional space, and the model has learned to place texts with similar meaning near each other.

1. TokensThe text is split into word pieces the model knows.
carriedoverunuseddays
2. AttentionA transformer reads all pieces together: each word looks at the others, so "leave" next to "annual" means time off, not "leave the office".
3. One vectorThe layers are pooled into one list of 768 numbers that describes the whole text.

How it learned: during training the model saw billions of text pairs. Pairs that mean the same (a question and its answer) were pulled together, unrelated ones pushed apart. After enough of this, distance in the space works like difference in meaning. This is called contrastive learning.

Key idea: no single number means "leave" or "laptop". Meaning is spread across all 768, like a fingerprint. That's why you can't read a vector, only compare it.

    STEP 4 · COMPARE (COSINE SIMILARITY)

    "Similar meaning" = small angle between arrows

    Think of each vector as an arrow from the centre of the space. Two texts are similar when their arrows point the same way. Cosine similarity measures exactly that: the cosine of the angle between the arrows.

    • 1.0: same direction, same meaning.
    • 0: at right angles, unrelated.
    • −1: opposite directions.

    Why the angle, not the distance? The arrow's length depends on things like text length, not meaning. Cosine ignores length: drag the length slider and the score stays the same. (Gemini's vectors here have length 0.59, not 1. Cosine doesn't care.)

    In pgvector: a <=> b gives the cosine distance (1 − cosine). The kit turns it back into similarity with 1 - (embedding <=> query).

    Real vectors have 768 numbers instead of 4, so the database does 768 multiplications, adds them up and divides by the two lengths. That's all cosine similarity is. With an index (step 5), Postgres does this for only a small set of candidates.

    STEP 5 · STORE (POSTGRES + PGVECTOR)

    One row per chunk: text, vector and keywords

    pgvector adds a vector column type to Postgres, plus fast "closest vector" search. Each chunk is saved as one row, so meaning search, keyword search and normal SQL (filters, joins, deletes) all work on the same data.

    • content: the chunk's text, shown to the AI and in the sources.
    • embedding: the 768 numbers, for meaning search.
    • tsv: the words reduced to their roots ("carried" → carri), for keyword search.

    The index (HNSW): comparing a question with every row is fine for 100 rows and far too slow for 10 million. HNSW links each vector to its nearest neighbours in layers, like a map with motorways and local roads. A search hops from neighbour to neighbour towards the question instead of checking everything.

    A real row in the chunks table

    REAL
    -- the kit's migration (backend/sql/migrations/001_init.sql)
CREATE EXTENSION IF NOT EXISTS vector;
embedding  vector(768) NOT NULL,
tsv        tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

-- meaning search: the closest 20 chunks to the question
SELECT content, 1 - (embedding <=> :question_vector) AS similarity
FROM chunks ORDER BY embedding <=> :question_vector LIMIT 20;

    Exact search vs the HNSW index

    SIMULATION
    Exact (no index)–comparisons, always finds the true nearest
    HNSW (the kit's index)–comparisons, hops along the links

    At 10 million chunks an exact search does 10,000,000 comparisons per question; HNSW typically does a few thousand. The trade-off: HNSW is approximate and can very rarely miss the single best match, which is why the kit fetches 20 candidates, not 1.
